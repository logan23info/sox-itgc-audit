Core concept

Application controls vs. ITGC

The most commonly confused distinction in SOX auditing. Understanding where ITGC ends and application controls begin — and why the difference matters for testing — is foundational for every auditor.

AS 2201 aligned Control classification Testing guidance
The fundamental difference

What each type of control actually does

Both are tested under SOX Section 404, but they address different risks and require different testing approaches.

IT General Controls (ITGC)

Apply broadly across the IT environment — not to a specific application or transaction. They protect the integrity of the infrastructure that all applications run on. If ITGCs are weak, you cannot rely on any application control that depends on them.

  • Who can access systems (Logical Access)
  • How changes are controlled (Change Management)
  • How systems are operated and monitored (Computer Operations)
  • How new systems are built and deployed (Program Development)
PCAOB: AS 2201 Para .26–.29 · COSO: CC6–CC8 · COBIT: DSS05, BAI06, DSS01

Application Controls

Operate within a specific application to ensure individual transactions are processed correctly, completely, and accurately. They directly prevent or detect misstatements in financial data.

  • Input controls (field validations, mandatory fields, format checks)
  • Processing controls (three-way match, duplicate invoice check)
  • Output controls (report balancing, reconciliation controls)
  • Interface controls (data transfer completeness between systems)
PCAOB: AS 2201 Para .30–.35 · COSO: CC6.1, CC7.1 · COBIT: APO11, DSS06

The dependency relationship — why ITGC comes first

Financial statements
What management certifies and auditors attest to
↑
Application controls
Three-way match, field validations, duplicate checks — only reliable if ITGCs work
↑
IT General Controls (ITGC)
Logical access, change management, operations, program development — the foundation
Critical auditing principle: If ITGC fails (e.g., developers can push unapproved changes to production), auditors cannot rely on application controls in that system — even if the app controls themselves appear to be working. The ITGC failure poisons the entire layer above it.

The middle ground

IT-dependent manual controls (ITDM)

The most commonly misclassified control type — and the one with the most testing complexity.

An IT-dependent manual control relies on a system-generated report (IPE) as its input. If the report is wrong, the control is wrong — even if the human reviewer performs it perfectly. This makes IPE validation under AS 1105.10A critical for every ITDM control.

Fully automated control

Performed entirely by the system with no human involvement. Test once by verifying the control is configured correctly and the configuration hasn't changed.

Test: Config + ITGC CM

Example: System blocks duplicate invoice numbers at point of entry

IT-dependent manual control

Human reviews a system-generated report (IPE) and takes action based on it. Requires both IPE validation AND sample testing of the human review step.

Test: IPE validation + TOC sample

Example: Manager reviews system-generated exception report and signs off monthly

Purely manual control

Performed entirely by a human with no system input. Test by sampling evidence that the human performed the control as designed.

Test: TOC sample only

Example: CFO manually reviews and approves journal entries over $50K before posting

Testing approaches

How to test each control type

1

Perform a walkthrough of the ITGC process

Trace one instance of the control through the entire process — observe it being performed, inspect evidence, confirm design understanding. Required by AS 2201.34 for all significant processes.

2

Obtain the control population (and validate as IPE)

For controls like access reviews or change management, obtain the population of all instances during the period. Validate completeness and accuracy per AS 1105.10A before sampling.

3

Select a sample based on control frequency

Daily → 25 items. Weekly → 10. Monthly → 3–5. Quarterly → 2. Annual → 1. High-risk controls get an uplift. Document the selection methodology.

4

Test each sample item for design and operating attributes

For each sample, verify every attribute of the control — authorization, timeliness, completeness, accuracy. One attribute failing = one exception. Document the result.

5

Conclude and document

Conclude on whether the control operated effectively for the period. Elevate any exceptions to the deficiency log with a classification (CD / SD / MW).

Fully automated controls only need to be tested once per period — verify the configuration is correct and that change management controls prevented unauthorized changes to the config. No sample testing of individual transactions is required.
1

Identify the automated control and its system configuration

Document exactly how the control is configured in the system (e.g., field validation settings, workflow rules, matching logic). Obtain a configuration screenshot or system-generated report.

2

Verify configuration is correct and complete

Confirm the configuration matches the control design. For example, for a three-way match — verify matching tolerance, what happens when there's a discrepancy, and what exceptions are flagged.

3

Verify ITGC supports reliance on the automated control

This is the key step. If change management controls are strong (CM-01 through CM-03 operated effectively), you can rely on the configuration being stable throughout the year without re-testing each transaction.

4

Verify no unauthorized changes occurred

Confirm through change management testing that no changes were made to the application or its configuration during the period that could have affected the automated control's operation.

IT-dependent manual controls require two layers of testing: (1) validate the IPE the control relies on, and (2) test that the human reviewer actually performed the review effectively.
1

Identify the IPE — the system-generated report used in the control

Document what report or data extract the reviewer uses. Identify the system that generates it, the parameters used, and who produces it.

2

Validate the IPE (AS 1105.10A)

Verify the report is complete (all relevant records included) and accurate (calculated correctly). Reconcile totals to an independent source. Document the validation procedure — this is a mandatory step and the most common PCAOB finding.

3

Sample the human review step

Select a sample of instances where the reviewer performed the review. For each, obtain evidence that the review was performed — signed report, approval in system, email sign-off — and evaluate whether the review was meaningful (not just a rubber stamp).

4

Evaluate exception handling

If the IPE report flags exceptions, verify the reviewer identified and acted on them. A reviewer who signed off on a report with obvious exceptions did not perform an effective control.

1

Confirm the control is truly manual — not system-assisted

If the reviewer uses any system output (a report, a list, an export) to perform the control, it's an IT-dependent manual control — not a purely manual one. Classification affects the testing approach significantly.

2

Obtain the population of instances

Document how many times the control was performed during the period. For a daily review, that could be 250 instances. Determine the sample size based on frequency.

3

Test each sample item

For each sampled instance, obtain evidence the control was performed — signed document, system log, email, timestamp. Verify all required attributes were checked (authorization, completeness, timeliness).

4

Evaluate quality of performance

Purely manual controls often fail not because the reviewer didn't sign off, but because the sign-off was perfunctory. Inspect the evidence for signs of genuine review — questions raised, corrections made, time stamps that are plausible.
