ERP control guides — SAP, Oracle & NetSuite

Each ERP has unique terminology, transaction codes, and evidence sources for ITGC testing. This guide covers what to request, where to find it, and common deficiency patterns for the three most common SOX ERPs.

SAP Oracle EBS / Fusion NetSuite
SAP uses transaction codes (t-codes) and authorization objects to control access. SoD conflicts are managed via the GRC (Governance, Risk & Compliance) module. Evidence is typically extracted from SM20 (Security Audit Log), SU01 (user master), and SUIM (user information system).

SAP-specific common deficiencies

SAP_ALL in production

The SAP_ALL profile grants every authorization in the system. Even one user with this profile is an immediate high-risk finding. No business justification exists for SAP_ALL in production.

Remove SAP_ALL from all production user IDs. Use specific roles with minimum necessary t-codes only.

Developers with PRD access

Developers need DEV client access, not production. When the same user ID exists in both DEV and PRD, SoD between change creation and promotion is broken.

Maintain separate user IDs per client, or confirm developer IDs are locked in PRD. Test with SUIM cross-client comparison.

GRC but no mitigation controls

GRC identifies SoD conflicts but management signs off on them without implementing compensating controls. The conflicts accumulate unaddressed year after year.

Every open SoD conflict must have a documented, tested mitigation control or role remediation with a closure date.
Oracle EBS uses responsibilities and functions for access control. Oracle Fusion (Cloud) uses roles, data security policies, and the Security Console. Evidence sources differ significantly between EBS and Fusion — confirm which version is in scope.

Oracle EBS — key evidence sources

  • User responsibilities — FND_USER_RESP_GROUPS table or Security Console
  • Concurrent program access — SRS (Standard Report Submission) by responsibility
  • Last login date — FND_LOGINS or OAM System Dashboard
  • SoD conflicts — Oracle GRC (Governance, Risk, Compliance) module reports
  • Change management — Patch log from AD_APPLIED_PATCHES; custom object change history
  • Audit trail — AuditTrail+ configuration; Oracle Audit Vault

Oracle Fusion Cloud — key evidence sources

  • User role assignments — Security Console → Manage Users; BICC extract
  • Duty roles and data security — Security Console → Manage Roles; Role Hierarchy report
  • Sign-in audit — Audit Reports under Tools → Audit Reports
  • Change management — Oracle sandbox promotion log; Update Manager patch history
  • SoD analysis — Oracle Risk Management Cloud (RMC) — access risk analysis
  • SOC 1 report — Oracle's SSAE 18 SOC 1 Type II covers hosted infrastructure

Oracle-specific common deficiencies

System Administrator responsibility over-assigned

The Oracle EBS "System Administrator" responsibility provides access to user management, concurrent programs, and profile options — a critical SoD conflict if assigned alongside financial transaction roles.

Restrict System Administrator to IT team only. No user with financial transaction responsibilities should hold it. Test via FND_USER_RESP_GROUPS cross-reference.

Custom responsibilities not reviewed

Standard responsibilities are well documented, but custom responsibilities created for specific users or sites are often excluded from access reviews — they don't appear in standard reports.

Extract all responsibilities including custom ones (CUSTOM% prefix). Include in access review population. Validate that custom responsibilities have documented business justification.
NetSuite is a multi-tenant SaaS ERP. Oracle provides a SOC 1 Type II for the platform infrastructure. Your company controls roles, permissions, and data within the tenant. Evidence is obtained from the NetSuite UI, SuiteAnalytics, and audit trail reports.

Key evidence sources in NetSuite

  • User list with roles — Setup → Users/Roles → Manage Users; export to CSV
  • Role permissions — Setup → Users/Roles → Manage Roles → Permissions tab
  • Login audit trail — Setup → Audit Trail → User Login Audit
  • Change audit trail — Setup → Audit Trail → System Notes → by record type
  • Custom scripting changes — Customization → SuiteScript → list of deployed scripts with modified dates
  • User last login — User record → Last Login field; export via SuiteAnalytics

NetSuite-specific common deficiencies

Administrator role over-assigned

The NetSuite Administrator role grants full system access. Multiple users often have it for convenience. Any user with this role can approve their own journal entries, override restrictions, and modify other users.

Restrict Administrator to 1–2 named IT owners. Finance users should have custom roles with only the minimum necessary permissions. Test quarterly.

SuiteScript changes deployed without approval

Custom scripts (SuiteScript) can modify financial calculations, approval workflows, and data transformations. Changes deployed directly to production without a change ticket bypass the CM control.

All SuiteScript deployments require a change ticket with business approval. Test via the deployment log and cross-reference to change management system.
