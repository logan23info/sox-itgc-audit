Common ITGC mistakes & how to fix them

The same deficiencies appear in PCAOB inspection reports year after year. This is a practical field guide to the most frequent ITGC failures by domain — what auditors find, why it happens, and exactly how to fix it.

By domain

Deficiencies by ITGC domain

Each tab covers the most common failures auditors find, why they occur, and the specific fix for each one.

Terminated users retain access after separation

The single most common ITGC deficiency across all industries. An access listing reviewed quarterly shows users who left the organization 30–90 days ago still have active accounts. The deprovisioning process depends on HR notifying IT, which often breaks down.

Fix: Automate deprovisioning via HR system integration. The moment a termination is entered in HR, a workflow triggers immediate access revocation across all in-scope systems. Target: revoke within 24 hours. Test monthly with a terminated employee sample.
Common MW trigger AS 2201 Para .26

Access reviews completed but not meaningful

Managers certify access lists without genuinely reviewing them — approving everyone on the list in bulk within seconds, or certifying people who no longer report to them. Auditors call this "rubber stamping" and treat it as an operating effectiveness failure even though the review was technically completed.

Fix: Require reviewers to see role descriptions, last login date, and employment status for each user. Implement a "certify individually" workflow rather than bulk approval. Train managers on what they're certifying — accountability matters.
Significant deficiency risk

Shared accounts and generic logins

Multiple users sharing one login ("admin", "finance_user", "batch_process") means no individual is accountable for actions taken with that account. Audit logs cannot tie an action to a person. Auditors cannot rely on any log-based control for that account.

Fix: Enforce a named-account policy. Each human user gets their own account. For batch processes, create dedicated service accounts with minimal permissions, documented business justification, and quarterly review.

Unresolved SoD conflicts with no compensating controls

A user with both AP entry and AP approval access can create a fictitious vendor and approve payments to themselves. SoD conflict matrices are often documented but never acted on — conflicts sit open for quarters without compensating controls.

Fix: For every identified SoD conflict: either remove one of the conflicting roles (preferred), or implement a documented compensating control (e.g., management review of all transactions by this user). Test compensating controls as rigorously as the primary control.
High fraud risk

Non-human identities (NHI) excluded from access reviews

Service accounts, API keys, and bots are provisioned for projects and never decommissioned. They accumulate excessive permissions over time and are never reviewed because nobody included them in the quarterly access review scope.

Fix: Build an NHI inventory. Include all service accounts and API keys in quarterly access reviews. Assign a human owner to each NHI. Decommission within 30 days of the project end date.

Approval dated after the deployment

A change ticket shows a deployment timestamp of Monday 9pm but an approval timestamp of Tuesday 10am. The auditor samples this change — it's an immediate exception. The change was deployed before authorization was obtained, regardless of whether the change itself was benign.

Fix: Implement system-enforced sequential workflow — the deployment step is locked until the approval step is completed. Remove the ability to retroactively edit timestamps. Train developers that "getting approval after" is never acceptable.
Top inspection finding AS 2201 Para .28

Emergency change process used routinely

Emergency changes should be rare (under 5–10% of all changes). When 30–40% of changes are classified as "emergency," it signals that the standard process is being bypassed systematically. This is a design deficiency — the emergency exception has become the normal path.

Fix: Define a strict emergency change definition (production outage or active security breach only). Require CISO/CTO approval for emergency classification. Report emergency change rates monthly to management. Any rate above 10% triggers a process review.

Developers with production access

When developers can directly deploy to production, there is no separation between those who build code and those who control the production environment. This means a developer could introduce unauthorized changes without detection — a fundamental ITGC failure.

Fix: Restrict production access to a dedicated release management team or automate via CI/CD pipelines where only approved builds can deploy. Test by cross-referencing the developer access list to the production environment access list — zero overlap should exist.
Common MW trigger

Cloud and SaaS configuration changes not tracked

Organizations track changes to on-premise ERP systems rigorously but forget that Salesforce, Workday, or cloud infrastructure configuration changes also affect financially significant processes. These changes often bypass change management entirely.

Fix: Extend change management scope explicitly to include cloud/SaaS configuration changes. Use each platform's audit log as the change population. Require the same ticket-approval-test workflow for SaaS config changes as for on-premise code changes.

Backup job "green" but restore never tested

Backup logs show all jobs completing successfully — but the organization has never tested whether the backups can actually be restored. Auditors test the restore test, not just the backup job. A green backup log is not evidence of recoverability.

Fix: Schedule and document quarterly restore tests for all financially significant systems. The test should restore to a non-production environment and verify data integrity. Document the results — a successful restore log is your evidence.
Frequently inspected

Batch job failures not monitored — or alerts not actioned

Either: (a) no monitoring exists and nobody knows a financial batch job failed, or (b) monitoring exists but failed jobs sit in an alert queue nobody checks. Either way, incomplete batch processing means incomplete financial data.

Fix: Implement automated alerting with escalation. Each failure alert must be assigned to a named owner with a resolution SLA (e.g., 4 hours for critical). Document resolution in a ticket system. Auditors need a sample of failure → alert → ticket → resolution.

DR plan exists but has never been tested

A disaster recovery plan documented in 2022 that has never been exercised is not a functioning DR control — it's a document. PCAOB requires evidence of an actual test, not just the existence of a plan.

Fix: Schedule an annual DR test with clear scope (which systems, what scenario), documented results (what worked, what failed), and management sign-off. Lessons learned must be tracked to closure. This is a detective control — test it like one.

UAT performed by IT — not by business users

IT tests the system themselves and signs off on UAT. This defeats the purpose of UAT, which is to have the business validate that the system works as the business needs it to — not just that it works technically. Auditors inspect who signed the UAT sign-off sheet.

Fix: Require that UAT is signed off by named business owners — Controller, VP Finance, or equivalent. IT can support UAT but cannot be the sole approver. Document this requirement in SDLC policy and verify it in every sampled implementation.

Data migration not reconciled

When a new system goes live, data migrated from the legacy system is not reconciled. Total record counts, key financial balances, and data integrity are not validated before or after cutover. Auditors find this immediately — without a reconciliation, reliance on migrated data cannot be placed.

Fix: For every migration, document a migration plan with: (1) pre-migration extract counts, (2) post-migration load counts, (3) financial balance reconciliation, and (4) business sign-off confirming the data looks right. This is non-negotiable for any SOX-significant system migration.
Common MW for new systems

No post-implementation review performed

Go-live happens, the project team disperses, and nobody formally validates that the controls designed for the new system are operating as intended 60–90 days later. Deficiencies introduced at go-live compound undetected.

Fix: Build a 90-day post-implementation review into every significant project plan before go-live. Assign a named owner. The PIR should assess whether controls designed in the system are operating and whether any new risks emerged post-launch.

JE population not validated as IPE

The most cited JE testing deficiency in PCAOB inspections. Auditors extract the JE population and begin testing without first validating that the population is complete and accurate. If the GL extract excluded certain ledgers or journal types, the entire test is built on an incomplete foundation.

Fix: Before any JE selection, validate the population: (1) reconcile record count to the GL trial balance, (2) document the parameters used in the extract, (3) confirm automated entries are included. Document this validation as a separate step in the workpaper.
#1 JE finding AS 1105.10A

After-hours entries not segregated for review

All journal entries are tested from a single undifferentiated sample — the after-hours and period-end entries with elevated fraud risk are not explicitly identified and tested. This is a required element of JE fraud risk procedures.

Fix: Segment the JE population before sampling: (1) after-hours and weekend entries, (2) period-end entries (last 3 days of month/quarter), (3) entries by infrequent or new preparers. Test each segment with targeted criteria and document the segmentation rationale.

JE preparer can also approve — no SoD

The access control over who can post journal entries also needs to be tested as a preventive control. A system that allows self-approval of journal entries has a fundamental SoD conflict that makes every other JE control weaker.

Fix: Verify the JE workflow enforces preparer ≠ approver at the system level — not just as a policy. Test this as LA-07 (JE posting access) and document the configuration evidence. Include it in the SoD matrix review.

Control narrative doesn't match how the control actually operates

The RCM says the control is performed "monthly by the IT Security team" but the walkthrough reveals it's actually performed quarterly by a different team using a different tool. Outdated documentation creates a walkthrough finding before testing even begins.

Fix: Update control narratives at least annually — and immediately after any process change. Assign each control a named owner who certifies the narrative is current. Treat the walkthrough as an opportunity to verify accuracy, not just confirm understanding.
Top walkthrough finding

Workpaper has no written conclusion

Testing is documented — procedures, evidence, sample items — but the workpaper ends without a written conclusion on whether the control operated effectively. PCAOB AS 1215 requires the auditor to document their conclusion, not just their procedures.

Fix: Every workpaper must end with an explicit conclusion statement: "Based on procedures performed, the [control name] control operated effectively for the period [date] to [date]. No exceptions were noted." Or if exceptions: "Exception noted — see deficiency log ref [#]."
AS 1215

Workpaper completed after the 14-day window

PCAOB AS 1215 requires audit documentation to be assembled and completed within 14 days of the report release date. Documentation completed after this window requires special justification and may still be treated as a documentation deficiency.

Fix: Build the 14-day window into engagement planning. Set internal deadlines for workpaper review that account for the 14-day close. Never rely on "we can finish documentation after fieldwork" — start documentation during fieldwork.

Evidence obtained but not tied to control attributes

An auditor obtains a screenshot of an approval email and attaches it to the workpaper — but the workpaper never explains which attribute of the control this evidence supports, or how the auditor evaluated it. The evidence is there; the evaluation isn't.

Fix: For each piece of evidence, write one sentence explaining: (1) what attribute it demonstrates, (2) how you evaluated it, and (3) the result. "Obtained approval email dated [date] from [approver name] — confirmed approval was obtained before deployment on [date]. No exception."
Pre-audit checklist

Auditor's pre-testing checklist — avoid the common mistakes

Run through this before starting fieldwork on any ITGC engagement.

Before you test any control

  • Control narrative reviewed and walkthrough completed
  • Control objective, risk rating, and assertion documented
  • Population obtained and IPE validation completed
  • Sample size calculated and methodology documented
  • Evidence request sent to control owner with due date

Before you close the workpaper

  • All sample items tested and documented
  • Each piece of evidence tied to a control attribute
  • Exceptions identified and logged in deficiency register
  • Written conclusion on operating effectiveness included
  • Reviewer sign-off obtained with date
  • Workpaper within 14-day documentation window
